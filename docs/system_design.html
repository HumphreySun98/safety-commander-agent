01Problem & goal

SafetyCommander runs the safety officer's observe → roll-up → plan line across DAY / WEEK / MONTH, autonomously:

  • DAY — watch the floor on video, judge each event vs the policy, act (log / notify / escalate / ticket / Slack), hand a shift report.
  • MONTH — roll the logged events up into KPIs: violation rate, trends, top hazards, open corrective-action backlog (kpi_report.py).
  • WEEK — the model reasons next week's inspections + toolbox talks + training (when / who / what), each tied to the hazard and the policy/OSHA clause (planner.py).

The agent proposes; humans confirm & execute. Still out of scope: permits/sign-offs, fire drills, environmental records, JHAs — the deeper process/compliance tasks. Pitch it as observe→roll-up→plan, not "the entire role".

The 3 "agent" pillars (demo must show all)

  • Reasoning model — a frontier model does the thinking, not regex/if-then.
  • Workflow tools — safety log, supervisor notify, corrective actions, escalation, handoff.
  • Autonomous — runs watch→decide→act→report on its own.

The 4 judging questions

  • Real operational problem?
  • Is the model reasoning, or the developer? Hardcoded rules don't count.
  • Believable, feasible end-to-end?
  • Would you show it to an ops manager?
North-star invariant: the VLM decides the risk level by reading the written policy (+ retrieved regs + detector facts). No code path maps a hazard to a risk level. This is the whole differentiator (judging #2).

03Reasoning core — the VLM judge

vlm_judge.py is the only place a verdict is formed. It builds one prompt from four parts and calls the shared Qwen3-VL endpoint (OpenAI-compatible).

Prompt partSourceRole
System promptconstant"You are a safety officer; reason from the policy; cite the clause; output JSON."
SAFETY POLICYsafety_policy.txtthe editable house rules (full text, in-context)
RETRIEVED REGSrag.py → knowledge/OSHA/SOP/SDS chunks relevant to the scene
DETECTOR FACTSperception/<frame>.jsonYOLO measurements (counts, distance, PPE)
SHIFT CONTEXT + image(s)orchestratorzone/ops + base64 frame(s)

Hardening: tolerant JSON parse + JSON-mode fallback; a grounding instruction (only assert what's visible → no hallucinated criticals); temperature=0 (reproducible).

{
  "observation": "...", "hazard_type": "forklift_obstructed_view",
  "risk_level": "none|low|medium|high|critical",
  "policy_clause": "2.x / OSHA 1910.178(n)(6) / SOP-FK-01 ...",
  "reasoning": "...", "recommended_actions": ["..."]
}

04The grounding stack (the core idea)

Three independent layers feed the judge. Each supplies a different kind of input; none decides risk.

LayerSuppliesOwnerOptional?
① Perception (YOLO)measurements — person/forklift counts, person↔forklift distance (m), PPE-missing, fire/smoke/spill/phone boolsByes → no-op if absent
② RAG (retrieval)knowledge — the specific OSHA standard / plant SOP / SDS for the sceneAyes → no-op if empty / SC_RAG=0
③ Policyrules — the site's editable risk classification & clausesArequired
This mirrors how a real safety officer thinks: see (perception) → consult the rulebook + regulations (policy + RAG) → judge (VLM). It also matches the literature (Bi-stage RAG + visual-LLM for safety compliance).

08RAG subsystem — redesigned (hazard-driven, citation-only)

What was wrong (v1, measured A/B n=8): a generic zone+ops query ran every frame and injected top-3 above a 0.02 threshold → it always pulled the same broad SOP, and the retrieved text induced hazards the model couldn't see (verdict changed in 7/8, mostly false HIGHs). Root cause: query not scene-specific, and RAG ran before the judgment.
Redesign principle: RAG is not a perception aid. Visual evidence decides whether a hazard exists; RAG only answers "which regulation does this already-seen hazard map to, and what do we cite in the incident log?" — auditability, not detection.

New flow — visual first, hazard-driven, gated, citation-only

  frame ─► PASS 1: judge(image + site policy + YOLO facts)  ──► hazard_type + risk tier
                                                                  │
        should_use_rag(hazard, risk)?  (risk ≥ medium  AND  a regulable hazard)
                                                                  │ yes
        build HAZARD-SPECIFIC queries (forklift_near_miss / ppe / smoke_fire / spill / guarding)
                                                                  │
        retrieve ─► relevance gate (≥2 hazard keywords/chunk) ─► ≤2 on-topic clauses
                                                                  │
        PASS 2: re-judge with regs ──► enrich CITATION + reasoning ONLY
                                       (risk tier from PASS 1 is KEPT — never changed by RAG)
  safe frame (none/low) ─────────────► no RAG at all (no 2nd call, no pollution)

Three guards (rag.py)

GuardWhat it does
should_use_rag()fires only when risk ≥ medium AND the hazard maps to a regulation class — safe frames never RAG
build_queries() per hazardhazard-specific queries (forklift → pedestrian separation / obstructed view), not the generic zone
relevant_enough()keyword gate — a chunk needs ≥2 hazard keywords to be injected; drops off-topic regs (kills over-grounding)

Evidence priority (baked into the prompt)

Visual evidence first  →  site policy second  →  retrieved regs third.
Never infer a hazard from retrieved text. If a reg conflicts with site policy, follow the policy.

Result (verified): the risk tier is set by the visual pass and RAG never changes it (no more false HIGHs). RAG fires only on hazards — forklift → OSHA 1910.178, hardhat → 1910.132/.135, safe → nothing. Default off in the main loop (SC_RAG=1 to enable); the policy-flip climax stays RAG-free. It pairs with B's distance fact: YOLO "person @ 2.1 m" → pass-1 near-miss → RAG cites 1910.178.

Demo line: "Once the agent sees a forklift near-miss, it retrieves the matching OSHA clause so the incident log explains, on the record, why the action was taken." — auditability, not accuracy.

09Design invariants

InvariantHow it's enforced
No hardcoded risk (judging #2)perception = measurements; rag = knowledge; dispatch = routing. Grep finds no if hazard: risk=…. The VLM is the only judge.
Graceful degradationperception absent → VLM-only; knowledge empty / SC_RAG=0 → no-op. Each layer is optional.
Determinismtemperature=0 → same frame, same verdict (demo-safe).
Stability / fallbackpure-VLM path always runs; the policy-flip climax is RAG-free; main never broken by the enhancement layers.
Clean A/B seamone contract: perception/<frame>.json schema. A and B own disjoint files.

11Team split & contract

A agent reasoning + RAG + orchestration + demo  ·  B perception (YOLO → facts) on the 4090.

12Open decisions — please review

D1 · RAG query strategy — RESOLVED: hazard-driven query + keyword relevance gate + two-pass, citation-only. The visual pass owns the risk tier; RAG never changes it.

D2 · RAG scope — RESOLVED: only on suspected hazards (risk ≥ medium & regulable). Safe frames get no RAG. Off by default (SC_RAG=1).

D3 · Scene signal source — RESOLVED: PASS-1 hazard_type drives retrieval (no extra caption call); B's forklift/PPE facts sharpen PASS 1.

D4 · Eval methodology — OPEN: small slide — 8 clips × {expected hazard, model risk, false positives, citation present, latency}. Do before demo.

D5 · Local-VLM fallback (4090) — ADOPTED: Qwen2.5-VL-7B-Instruct via vLLM OpenAI API; switch = one .env line. Break-glass only (rehearse/demo on the 30B endpoint); must validate it emits our JSON schema before trusting it.

D6 · RAG narrative — RESOLVED: positioned as auditability (cites OSHA on the hazard frame), not a blanket accuracy boost.
